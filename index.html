Data platforms

Real-time POS streaming

Kafka → Snowpark → Snowflake Streams/Tasks → data marts

Problem

Point-of-sale data arrived through point-to-point integration flows that were brittle under peak load and hard to replay, so reporting lagged and recoveries meant manual backfills.

Architecture

Key decisions

  • Kafka as the system of record for events, so consumers can replay from offsets instead of re-requesting data from stores.
  • Land raw payloads as VARIANT first, then parse with Snowpark — schema changes don't break ingestion.
  • Streams & Tasks for incremental, CDC-style merges into curated tables; dbt owns the mart layer.
  • Error monitors with automatic reprocessing of failed micro-batches.

Outcome

Near-real-time sales visibility on a pipeline that recovers on its own, replaces fragile integrations, and gives downstream teams a single trusted feed.

Catching a silent vendor data rewrite

Detecting retroactive changes in third-party history

Problem

A third-party source quietly restated historical records. Loads still succeeded and row counts looked normal, but trends shifted under analysts' feet with no change notice.

Architecture

Key decisions

  • Keep every vendor delivery as an immutable, append-only snapshot, so history can always be compared and rolled back.
  • Hash closed historical periods on every load; any fingerprint change in a "closed" window is a restatement.
  • Data-quality tests on distributions, not just nulls and counts, gate promotion to curated tables.
  • Quarantine suspect loads and alert owners instead of silently overwriting.

Outcome

Restatements surface as explicit, reviewable events instead of mystery trend shifts, and the vendor contract now has a technical enforcement point.

Agentic AI: agents that ask instead of guess

Two systems I designed and built end to end (data layer, agents, and UI) around one idea: reliable agents know when not to act.

Multi-agent · Full-stack

Agentic API Orchestrator

A multi-agent chat assistant that turns plain-English questions into authenticated enterprise API calls: it picks the right API, reads its contract, collects missing fields, runs the request, and explains the result.

Designed and built end to end: multi-agent LangGraph orchestration, FastAPI backend, React chat UI, MongoDB-backed knowledge and retrieval, OAuth-authenticated API execution, interactive clarification and form loops, and a registry/contract model for onboarding new APIs.

Architecture & design details

Architecture layers

  1. 1Web UIReact + TypeScript + Vite, chat with markdown answers and a visible agent trace
  2. 2API serverFastAPI
  3. 3Agent orchestrationLangGraph state machine with interrupt/resume
  4. 4Knowledge baseMongoDB + JSON source-of-truth files
  5. 5External servicesLLM gateway, embedding gateway, OAuth token service, target APIs

Hybrid intelligence

  • LLM only where language judgment is needed: routing refinement, value extraction, explanation.
  • Deterministic code for everything else: contract parsing, payload shaping, auth, REST/GraphQL execution.
  • Guardrails: never invent missing identifiers or facts that aren't in the API response.
  • Fuzzy selection, exact execution: capability cards are embedded and retrieved by similarity, then the chosen API's contract is fetched exactly. Keyword scoring is the fallback when vector retrieval is off.

Interaction design

Clarification cards

When routing confidence is low, the user picks the API instead of the agent guessing silently.

Scenario cards

APIs with more than one request shape offer lookup scenarios to choose from.

Contract-driven forms

Editable payload forms generated and validated from the OpenAPI contract, not hand-built per API.

Smart auto-run

If the message already supplies everything for exactly one lookup, it just runs.

Post-answer quick actions

Edit the same payload or switch scenarios without restarting the conversation.

Memory & feedback

Session memory for chat history and per-API context, plus optional useful / not-useful feedback.
